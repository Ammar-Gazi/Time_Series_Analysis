The 32-Bit Signed Integer Overflow Bug (Avatar & Avengers: Endgame)Look closely at rows 4 and 5 in your screenshot:   Avatar (2009): gross_worldwide_usd = -1371256588, roi_multiple = -5.79   Avengers: Endgame (2019): gross_worldwide_usd = -1352306043, roi_multiple = -3.80   Why did this happen? imdb236's backend stored grossWorldwide in a 32-bit signed integer (INT), whose maximum value is $2,147,483,647$ ($2^{31} - 1$). Any movie that crossed $2.147 billion (Avatar at ~$2.92B, Avengers: Endgame at ~$2.79B) wrapped around into negative numbers via integer overflow!Exact mathematical recovery: Adding $2^{32}$ (4_294_967_296) to any negative grossWorldwide restores the exact original gross (-1371256588 + 4294967296 = 2,923,710,708 for Avatar, and -1352306043 + 4294967296 = 2,942,661,253 for Endgame). Fixing that in code is a huge flex on a Data Analyst / Data Scientist resume.

Time-Series Density (276 movies spanning 1977–2025)Right now, 276 movies spread across nearly 50 years gives roughly 5–6 movies per year—too sparse for a continuous monthly time series without huge zero-gaps.   If we query /api/imdb/search by release year (startYearFrom / startYearTo) from 2010 to 2025 (rows=50 per year = 16 API calls), we get ~600–800 modern releases tightly packed across 192 consecutive months (2010–2025)—ideal for monthly ARIMA, ACF/PACF seasonality, and walk-forward validation.
